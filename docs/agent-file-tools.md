# Generic Provider 受控文件工具

## 目的

`Provider response is too large` 不能仅靠持续提高响应上限解决。让模型把整份代码库、完整大文件或大量文件正文反复放进工具参数，会同时放大网络响应、Provider 上下文、Electron IPC 和本地持久化压力，也可能产生被截断的工具调用。

本应用将操作分成两条链路：

- Shell 命令必须使用 `terminal_execute`，继续进入同一个可见终端并沿用审批、Ctrl+C、认证交接和审计。
- 文本文件在用户显式授权后使用 `file_list`、`file_read`、`file_patch`、`file_write` 直接处理，不把文件内容伪装成终端命令。

## 权限边界

- 默认 `off`；可按当前 Generic Agent Session 选择 `read-only` 或 `read-write`。
- `read-write` 需要界面二次确认；权限不会跨应用重启持久化。
- 授权时将正式 Session 的规范化 `cwd` 固定为根。之后终端切换目录不会扩大文件权限。
- 本地文件使用 Node 文件 API；SSH 文件使用该可见终端现有 SSH Client 的 SFTP subsystem，不创建第二个 SSH 连接。
- 路径穿越、越界符号链接、被替换的授权根、Windows 设备名/备用数据流都会被拒绝。
- 覆盖现有文件必须携带最近一次读取返回的 SHA-256；修改使用临时文件和原子发布。
- 文件权限变更及成功写入会进入 Audit，但 Audit 不保存文件正文。

读取到的正文会作为完成当前请求所需的上下文发送给用户选择的 Generic Provider。Codex App Server 原生模式继续使用 Codex 自己的工作区与文件逻辑，不复用这组 Generic 工具。

## 有界工作流

- 单个文本文件读取/服务端写入上限为 512 KiB，仅支持有效 UTF-8。
- `file_write` 单次工具参数最多 131,072 字符；较大修改应优先使用小型精确 `file_patch`。
- 每个 Agent turn 的文件读取和目录列表序列化结果合计最多 2 MiB。
- 目录列表最多 500 项，单文件最多 64 个精确替换。
- 文件正文只保留一个推理步骤；完成后工具参数和结果会压缩为路径、字节数和哈希，避免后续轮次与持久化线程不断膨胀。

推荐流程：列出目标目录 → 只读取需要的文件 → 使用哈希保护的精确补丁 → 在可见终端运行测试/构建/部署命令 → 根据结构化命令结果继续修正。二进制或超大单文件仍应使用 SFTP 传输队列，删除、移动、权限调整等命令仍通过可见终端执行。
